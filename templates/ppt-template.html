10 / 22

规范先行，还是随意发挥？

① 原始需求
一份 PRD 定下整体布局与 UI 规范 —— 栅格与页面框架、色板、组件样式、交互约定
A CODEWAVE
整站统一
布局与视觉都按规范生成，页面之间"长一个样"，风格不漂移。
  • 布局栅格先定死
  • 色板与组件样式统一
  • 页面框架一次成型
B XXCODE
逐页漂移
没有规范约束，页面各写各的，风格发散，改一处崩一片。
  • 每个页面自己定样式
  • 视觉风格逐页漂移
  • 返工成本随页数上涨
③ Spec 过程回顾
CODEWAVE Spec 里有"设计规范 / 布局骨架"这一层 XXCODE 没找到 规范这一层根本不存在
④ 结论
规范不是画着好看的，是让 AI 每次落笔都有边界

④ 结论

痛点① 的解法 · 化整为零
13 / 22

不把整本 PRD 塞给 AI

01 →
需求结构化解析
把几十页 PRD 解析成结构化 Spec：大纲 + 标准词表 + 模块拆分，去掉冗余，只留 AI 真正需要的事实。
02 →
拆成原子任务
马具工程按依赖关系，把需求拆成一个个 ≤4 小时的原子任务，边界清晰、互不干扰。
03 →
按需准备上下文
每个任务只加载它用得到的那一小块：相关 Spec、组件、接口、规范——渐进式知识披露，绝不整本灌进去。
04
断点续跑 · 不丢上下文
Session 持久化 + 多 Agent 各带独立上下文窗口，长程任务可恢复，不受单次窗口大小限制。
化整为零、按需喂料——窗口再有限，也接得住大规模复杂需求，而且尽量不遗漏。

痛点③ · 自然语言的模糊
16 / 22
为什么 AI 生成的东西总"似是而非"

AI 不会跟你辩论，
它只会自己猜。

需求本身就有歧义，AI 不追问，只默默按自己的理解生成。问题不是"能不能澄清"，而是澄清有没有被标准化进流程——被强制发生、被记录、被下游消费。零散的对话式澄清，恰恰做不到这几点。

痛点③ · 自然语言的歧义
17 / 22

同一句话，AI 能理解出好几种

「做一个用户管理」
→ 只是增删改查？还是带角色权限、组织架构、审批流的完整体系？
「支持导出」
→ 导 Excel 还是 PDF？全量还是当前筛选？要不要按权限脱敏？
「列表要快一点」
→ 分页 / 虚拟滚动 / 加缓存？多大数据量才算"快"？
「和现有系统打通」
→ 打通哪个系统？实时还是批量？走 API 还是直连数据库？
AI 不会问你到底要哪种，它直接挑一种就开写——于是做出来的东西"看着对，其实不对"。
痛点③ 的解法 · 需求标准化 + 主动澄清
18 / 22

需求澄清是杠杆率最高的投入

规范文档本质是一个"认知对齐"工具——人、AI、团队先对齐"要做什么"，再动手写。

01 →
EARS 标准化
把模糊的自然语言写成"当…发生时，系统应…"的结构化规格：一句话十种理解，收敛到只剩一种。
02 →
主动澄清
遇到歧义打上「需澄清」标记，逐条追问，而不是自己猜着往下写。
03 →
契约先行 · 步进确认
需求 Spec 由人机共同确认后才生成；每一步可追溯、可回退。
04
澄清进流程
澄清被强制发生、被记录、被下游设计与编码消费——是标准化资产，不是零散对话。
把"人"这一环的熵和幻觉，尽量在需求阶段就消掉。
